# Build Notes — live box product

The repository ships ready-to-install MIPS binaries in `payload/bin/`. Rebuild
only when native source or embedded assets change. **Product truth is the live
hub / box snapshot**, not a later integration rebuild. The live
`box-snapshot-20260818` / `box-snapshot-20260819` webui identity is the current
product; the 778408-byte Recovery rebuild is a discarded inversion, not the
baseline.

## Target

- CPU: MIPS, big-endian
- Userspace: uClibc-era embedded Linux
- Output: mostly static helper binaries

## Toolchain — official Zig 0.16.0

All the Zig-built binaries use the official Zig 0.16.0 tarball (clang/LLD
21.1.0, executable SHA-256
`e6cd688d25664983833aae272f501d4bceeae304875b8f1741209d15fd13a4ec`). The build
script keeps separate `WEBUI_ZIG` and `OFFICIAL_ZIG` variables; both carry
that pin.

Verified 2026-10-27 on macOS (aarch64):

- Index: `https://ziglang.org/download/index.json`
- Tarball: `https://ziglang.org/download/0.16.0/zig-aarch64-macos-0.16.0.tar.xz`,
  52238004 bytes, SHA-256
  `b23d70deaa879b5c2d486ed3316f7eaa53e84acf6fc9cc747de152450d401489` (matches
  `index.json`)
- `zig` executable SHA-256
  `e6cd688d25664983833aae272f501d4bceeae304875b8f1741209d15fd13a4ec`,
  `zig version` 0.16.0, `zig cc --version` `clang version 21.1.0`

With it, all ten Zig-built binaries rebuild byte-for-byte, and a repeat
`codex_webui` build is identical.

Use this toolchain, not whatever `zig` is on `PATH`. The `codex_webui` built
from `8231751` (1189976 bytes, SHA-256
`974fe5442529ef2811ae7336eb242962e15301d909b74d04232dffda7b3db84e`) came from
Homebrew Zig 0.17.0 (clang/LLD 22.1.8). Its code and data differ from the
official 0.16.0 build of the same source, so it was replaced.

Box `codex_webui` builds up to 2026-10-20 (946744 bytes, SHA-256
`6061b907bde87592dce5f7e4fd74233b8f97666d1509eb43ae7125a780f020a4`) used Homebrew Zig 0.16.0_1 (clang 21.1.8), which Homebrew no longer
serves. Official Zig 0.16.0 rebuilds that binary with identical code and
data; only the 20-byte `.comment` compiler stamp differs.

### No `.pdr` section

Every Zig-built binary in `payload/bin/` and `payload/helpers/` links with
`-Wl,-T,build/discard-mips-pdr.ld` (not the fixed-address `hal_remotes` code,
which has its own layout). clang's MIPS backend writes a `.pdr` section
(procedure descriptors, an old debugging aid) for every function. Nothing
loads it, and `-s` doesn't remove it, yet it was 26-52 KB of each binary:
310 KB across the nine in `payload/bin/` and `codex_flash_free`, and as much RAM in each installer's staging area. The
script uses `INSERT`, so lld keeps its default layout and the loaded image is
unchanged. `tools/elf_load_cmp.py` checks that: it compares the entry point,
the program headers and the bytes of every segment of two ELF files, ignoring
only the section table that the loader never reads.

`dropbearmulti` keeps its `.pdr` on purpose. The installers hard-link the
copy harmony-hub-root leaves on the hub when it is byte-identical, which saves
far more flash than the section's 41 KB.

```sh
python3 tools/elf_load_cmp.py old/codex_webui payload/bin/codex_webui
```

### codex_webui

`harmony_shell_assets.h` is generated by `tools/package_harmony_shell.sh`
(bun 1.3.14) from `tools/webui-sim/public/`. `activity_ui_assets.h` is
generated by `tools/embed_activity_ui.sh` from `payload/web/activity-ui.*`.
Both regenerators reproduce the committed headers byte-for-byte.

Pinned source blobs:

- `payload/source/codex_webui.c` — `fe7491bd2db95d22fefa6d1f5bd1a247bc9e2ba3`
- `payload/source/harmony_shell_assets.h` — `6b78cfb311fe31e2bce2bd4be9cf4668a1fea6a8`
- `payload/source/activity_ui_assets.h` — `c64ccf038c79160a0995f3e4ec322c47130e2ca9`
- `payload/source/remote_skin_jpg.h` — `419611c5ff0713f1f5de2dd684d699f6d77238d5`

```sh
"$WEBUI_ZIG" cc -target mips-linux-musleabi -Os -static -s -Wl,-T,build/discard-mips-pdr.ld \
  -I payload/source \
  -o payload/bin/codex_webui \
  payload/source/codex_webui.c
```

Result must be `ELF 32-bit MSB executable, MIPS, MIPS32 rel2, statically
linked, stripped`, size 1349656, SHA-256
`337c70ec50f984334d082c86e534f946e80d7b2c32258b2e549377eb5768e40b`.

To compare against a Homebrew-built box binary, compare what loads: the
`.comment` compiler stamp differs, and box binaries still carry `.pdr`
(see *No `.pdr` section* above), and neither is loaded.

```sh
python3 tools/elf_load_cmp.py box_codex_webui build/output/codex_webui
```

### codex_androidtv (Official Zig, BearSSL 0.6)

Network control for Android and Google TVs ([ANDROID_TV.md](ANDROID_TV.md)).
TLS is BearSSL 0.6. Its source isn't in the repository: download
`https://www.bearssl.org/bearssl-0.6.tar.gz` (SHA-256
`6705bba1714961b41a728dfc5debbe348d2966c117649392f8c8139efc83ff14`; bearssl.org
publishes no checksum, this is the tarball as downloaded on 2026-11-07) and
unpack it in `build/tmp/`. Build from there, so BearSSL's paths are relative,
with the file list sorted (the link order, and so the output, depends on it):

```sh
cd build/tmp
"$OFFICIAL_ZIG" cc -target mips-linux-musleabi -Os -static -s -Wl,-T,../discard-mips-pdr.ld \
  -ffunction-sections -fdata-sections -Wl,--gc-sections \
  -Ibearssl-0.6/inc -Ibearssl-0.6/src \
  -o ../../payload/bin/codex_androidtv ../../payload/source/codex_androidtv.c \
  $(find bearssl-0.6/src -name '*.c' | LC_ALL=C sort)
```

Result must be `ELF 32-bit MSB executable, MIPS, MIPS32 rel2`, statically
linked, stripped, size 232824, SHA-256
`9a1423cf63ce3b56d7ee624e118d0ac8c62a2a670209baf16807e2fbf6f95817`
(`payload/source/codex_androidtv.c` blob `0a16343ec959eb7dcfca5ebb740aaa6a8dbbb3c2`).
The output doesn't depend on where the tree or BearSSL is unpacked. For the
fake-TV smoke test, build the same way with `-target x86_64-linux-musl` (or
your host) into `build/output/codex_androidtv-native`.

### codex_flash_free (installer helper, Official Zig, `-mcpu=mips32`)

The installers copy this probe into their RAM staging folder, run it to read
the free flash (`statfs` on `/data`; the hub's BusyBox has no `df`), and
delete it with the folder. It lives in `payload/helpers/`, not `payload/bin/`,
because it is never installed on the hub.

```sh
"$OFFICIAL_ZIG" cc -target mips-linux-musleabi -mcpu=mips32 -Os -static -s -Wl,-T,build/discard-mips-pdr.ld \
  -o payload/helpers/codex_flash_free payload/source/codex_flash_free.c
```

Result must be `ELF 32-bit MSB executable, MIPS, MIPS32`, statically linked,
stripped, size 27912, SHA-256
`749c055e9fdc5cea50d3f48d0775441bd758f6811ee32f625c5b423121854177`.

### busybox-extra (BusyBox 1.37.0, Official Zig, GPL-2.0)

A second, static BusyBox with the commands the hub's own BusyBox 1.13.4 lacks
([BUSYBOX.md](BUSYBOX.md)), installed as `busybox-extra` so it never shadows
the stock `busybox` on a `PATH` that puts `/data/codex/bin` first. Its corresponding source is the upstream tarball
plus [`third_party/busybox-1.37.0/`](../third_party/busybox-1.37.0/README.md):
one patch, the complete `.config` and BusyBox's LICENSE. The build script's
busybox section, `build/busybox-zig-cc.sh` and `build/busybox-zig-ar.sh` are
the build scripts. It needs GNU make and a host C compiler for kconfig
(`HOSTCC`, default `cc`), so it builds on Linux like Dropbear.

The script downloads `https://busybox.net/downloads/busybox-1.37.0.tar.bz2`,
checks it against `BUSYBOX_TARBALL_SHA256`
(`3311dff32e746499f4df0d5df04d7eb396382d7e108bb9250e7b519b837043a4`, matching
busybox.net's `.sha256`), applies `patches/*.patch`, and copies
`busybox.config` in as `.config`. It fails if `make oldconfig` would change
that file. Then, with `SOURCE_DATE_EPOCH=1727395200 TZ=UTC LC_ALL=C`:

```sh
make -C "$PWD/build/tmp/busybox-1.37.0" O="$PWD/build/tmp/busybox-out" -j"$(nproc)" \
  CC="$PWD/build/busybox-zig-cc.sh" AR="$PWD/build/busybox-zig-ar.sh" HOSTCC=cc \
  EXTRA_LDFLAGS="-s -Wl,-T,$PWD/build/discard-mips-pdr.ld" SKIP_STRIP=y busybox
```

Run it from the repository root. The paths must be absolute: `make -C` runs
in the source tree, so a relative `O`, `CC` or `AR` would resolve from there.

`BUSYBOX_ZIG` must name the pinned Zig (the script uses `OFFICIAL_ZIG`). The
compiler wrapper drops the GNU ld options BusyBox's `scripts/trylink` passes
that lld rejects or that only write a map file and a log. Result must be
`ELF 32-bit MSB executable, MIPS, MIPS32 rel2`, statically linked, stripped,
size 418688, SHA-256
`f516bde18556bfe4c63731f882bc06d02beed1f61dff92898fd9cd9773e6a3bc`. The script
copies it to `build/output/busybox-extra`. The output doesn't depend on
where the tree is.

### hal_remotes (the two-screen `hal` edits, Official Zig, `-mcpu=mips32r2`)

Not a binary. `payload/helpers/hal_remotes_patch.json` holds the edits the
installer applies to the hub's own `hal`
([TWO_SCREEN_REMOTES.md](TWO_SCREEN_REMOTES.md)); `tools/build_hal_remotes.py`
writes it from `payload/source/hal_remotes/` (freestanding C, no libc, linked
at fixed addresses) and checks the compiled code against its rules.

```bash
HAL_REMOTES_ZIG=<zig 0.16.0> python3 tools/build_hal_remotes.py --stock <stock hal, firmware 4.15.600>
```

`--stock` pins the patched md5 (`904560dfaa3dc84a175524c2a80ec240`), which
`payload/scripts/rcS.local` must name too. Without it the build keeps the
pinned md5 when the edits come out unchanged. `--check` fails if the file
differs from what the source builds. Needs `pyelftools`.

### dhcpd / portal (Official Zig)

Since issue #88, `codex_dhcpd` and `codex_portal` build with the same pinned
Official Zig 0.16.0 as the other first-party binaries (previously unpinned
Bootlin GCC builds). The build script verifies them fail-closed against
`DHCPD_EXPECT_SHA256` / `PORTAL_EXPECT_SHA256` (see the table above):

```sh
"$OFFICIAL_ZIG" cc -target mips-linux-musleabi -Os -static -s -Wl,-T,build/discard-mips-pdr.ld \
  -o build/output/codex_dhcpd payload/source/codex_dhcpd.c
"$OFFICIAL_ZIG" cc -target mips-linux-musleabi -Os -static -s -Wl,-T,build/discard-mips-pdr.ld \
  -o build/output/codex_portal payload/source/codex_portal.c
```

The Bootlin toolchain is still downloaded by the script, but now only for
the Dropbear build. The Dropbear source tarball is verified against
`DROPBEAR_TARBALL_SHA256`
(`0d1f7ca711cfc336dc8a85e672cab9cfd8223a02fe2da0a4a7aeb58c9e113634` for
`dropbear-2025.89.tar.bz2`, 2374006 bytes) before extraction, and the built
`dropbearmulti` must reproduce the committed binary
(`DROPBEAR_EXPECT_SHA256`, see the table above) or the script fails.

## Linux Build

The helper build script is written for a Debian/Kali-like Linux environment:

```sh
cd build
./build_harmony_tools_kali.sh
```

It downloads the Bootlin MIPS uClibc toolchain and Dropbear source into
`build/toolchains/` and `build/tmp/`, then writes fresh binaries to
`build/output/`. The committed `harmony_shell_assets.h` is the output of
`tools/package_harmony_shell.sh` (bun 1.3.14) over `tools/webui-sim/public/`,
so regenerating it is a no-op. The same holds for `activity_ui_assets.h` and
`tools/embed_activity_ui.sh`.

Deploy `codex_webui` and `codex_hbus` from the same build. Activity resource
updates use the fail-closed `payload/activity/codexactivity.lua` plugin and a
root-only volatile file channel, so the full ActivityList, MapList, and
FunctionList transaction never passes through a shell argument or firmware
network-sync command.

The host-side HBus smoke test deliberately sends notifications, a ping, an
unrelated response, and a fragmented 350 KB response before the matching
request ID:

```sh
cc -std=c99 -O2 -o /tmp/codex_hbus_host payload/source/codex_hbus.c
python3 tools/hbus_notification_smoke.py /tmp/codex_hbus_host
```

The activity save path also has a host-side regression for semantic JSON
comparison. It verifies that object-key order, escaped slashes, Unicode escape
forms, and equivalent numeric forms do not create false resource writes:

```sh
tools/activity_json_semantic_smoke.sh
```

The activity editor model regression verifies orphan-map repair, required
per-surface and activity-function-map creation, the zero/omitted local identity
format, and duplicate canonical button-ID rejection:

```sh
node tools/activity_ui_model_smoke.mjs
```

The offline guard rejects resource-proxy, firmware-sync, queue, socket, session,
and account-service paths in the activity writer. It also verifies that the
paired-remote HBus guards and reversible LAN-only route guard are packaged, and
that the installer references the exact `activity/codexactivity.lua` candidate
(accepting either the Windows backslash or portable forward-slash separator):

```sh
tools/activity_offline_guard.sh
```

The build script does not run these tests; run them yourself before
rebuilding.

After rebuilding:

1. Copy the required binaries from `build/output/` into `payload/bin/`.
2. Refresh `payload/bin/MANIFEST.txt`.
3. Deploy to a test hub with `install_webui.ps1` or `python3 install_webui.py`.
4. Confirm checksums and runtime behavior.

## Windows

Windows can deploy with PowerShell, and Linux/macOS can deploy with the Python
installer. Use WSL, a Linux VM, or the existing build server for rebuilding MIPS
binaries.

## Dropbear

`dropbearmulti` is included so the web UI package can keep SSH reachable on a
rooted hub. The installer does not replace `authorized_keys`; it only uploads
Dropbear binaries/wrappers and starts the service if needed. Its build status is
`UNVERIFIED_THIRD_PARTY` (see above).
